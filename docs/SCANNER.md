# Standalone scanner contract

## Integration surface

`src/index.ts` exports the framework-independent `runScan(store, input, createProviders, runtime)`, `admitJob`, `classifySignature`, `buildReport`, and range helpers. `RewardsStore` and `Providers` in `src/scanner/types.ts` define replaceable adapters. The engine receives a clock, cancellation signal, progress observer, unique job/run identities, fixed cutoff and finite limits. It does not import SQLite, CLI code or environment loading. Compile with `pnpm build`; local consumers can import `dist/index.js` and its declarations. No package is published.

```ts
import { runScan, buildReport } from './dist/index.js';
import { SqliteRewardsStore } from './dist/storage/sqlite.js';
import { createRealProviders } from './dist/providers/real.js';

// The adapter supplies dbPath, wallet, apiKey, cutoff, jobId and owner in memory.
const store = new SqliteRewardsStore(dbPath);
try {
  await runScan(store, {
    wallet, cutoff, jobId, owner,
    limits: {
      stonkfun: 20, helius: 200, pages: 200, resumes: 10,
      deadline: Date.now() + 3_600_000,
    },
  }, job => createRealProviders({ store, job, apiKey }), { now: Date.now });
  const report = buildReport(store, wallet); // Local reads only.
} finally { store.close(); }
```

Real providers support mainnet only and reject other networks rather than misattribute evidence. Injectable providers/storage can exercise other canonical networks. Jobs, coverage and classifications are scoped by `(network,wallet)`. A future hosted adapter must authenticate and authorize wallet/job/report access before calling the engine; a public wallet argument is not authorization. Separate database files do not share provider allocations, so a future service needs a shared allocator.

## Evidence and classification

Payout policy v2 is opt-in for the pure reconciler and always used by the scanner. V1 remains the default for existing callers. Normalizer/identity v1 is unchanged. Successful execution, proven positive net credits, recipient ownership, observed official quote membership, absence of wallet participation, and supported payout structure are necessary for confirmation.

V2 accepts parsed token transfers plus strictly decoded outer compute-budget instructions: actual program ID `ComputeBudget111111111111111111111111111111`, no accounts, no parsed override, no child instructions, known discriminators 1–4, exact payload lengths, little-endian parameters, valid heap alignment and no duplicate settings. Unknown instructions remain unresolved. Native balances must still prove only the fee debit; unknown setup/rent/claim/swap/LP flows are not ignored. Token-2022 transfers may confirm when all net credits reconcile and the exact official signature/mint aggregate equals gross or proven net. This records observed equality, not a general definition of feed `amountRaw`; allocations among launch rows remain unestablished.

Primary sources verified for this extension: [Solana SDK program IDs](https://github.com/anza-xyz/solana-sdk/blob/master/sdk-ids/src/lib.rs), [compute-budget instruction interface](https://docs.rs/solana-compute-budget-interface/latest/src/solana_compute_budget_interface/lib.rs.html), and [Solana transfer fees](https://solana.com/docs/tokens/extensions/transfer-fees). These establish instruction semantics and net-credit distinctions; accepting exact feed attribution with either observed aggregate relation is the scanner's inference, not newly published StonkFun fee semantics.

`Classification` records `confirmed`, `attributed`, `excluded` or `unknown_candidate`, reasons, basis/version, gross/net amounts, mint/program, recipient/source accounts and owners, authority, signers, fee payer, signature, evidence IDs and supporting signatures. Exact-feed support applies only to that transaction and does not require `transactionIndex`. Same-slot pattern support requires two distinct exact-feed witnesses in the same slot with provider-supplied transaction indexes on opposite sides of the candidate. Source account/owner, authority/kind/instruction signers, all transaction signers, fee payer, mint and program must match; every candidate transfer needs supported structure and witnesses. Missing relevant ordering emits `ordering_unavailable`; timestamps, feed order and response order never supply an index.

Historical-authority model v1 adds a distinct `verified_historical_authority` confirmation basis after exact-feed and same-slot checks. It derives consecutive witness-bounded epochs only from independently reconciled exact official-distribution signatures retained in the same database. Each interval is strictly interior to its two witness block times and at most one day wide; the one-day cap is a conservative scanner policy, not a provider guarantee. Both boundary witnesses must share the candidate's source account/owner, authority, mint/program, transfer structure, full signer set and fee payer. Exact wallet-owned positive net balance, raw transfer amount/decimals, no wallet address anywhere in transaction account keys, retained reward-launch/summary/distribution quote membership, and no unresolved normalization/ownership/identity conflict remain mandatory. Conflicting identities in the interval, overlapping epochs or local safety revocations block confirmation. Epoch boundaries, identity hash, model/classifier versions, witness signatures/evidence IDs and source/destination roles are retained per classification. Neither an observed address nor cross-database evidence implies lifetime validity. Most historical payouts may remain unknown.

Payout policy v3, which the scanner now selects, additionally interprets the recognized associated-token-account creation unit of [NORMALIZATION.md](NORMALIZATION.md): its two decoded positions are structure rather than uninterpreted activity, and its own `createAccount` lamports are the only extra native movement the reconciliation expects. Policy v2 keeps its previous meaning exactly.

Classifier v3 adds a separately reported `attributed` status with basis `distributor_pattern`. Classifier v4 adds the native-SOL lane and the three new no-transfer reasons below, and narrows gate G4 with the associated-token-account owner-seed allowance. It is an explicitly weaker claim and is never a confirmation. It runs only in the final unknown branch for a signature that no official row names, so exact-feed, same-slot and historical precedence is unchanged and an unreconciled exact-feed attempt is never downgraded to attribution. Gates G1–G6 run in fixed order, and an unknown row gains only the code of its first failing gate:

- G1: every wallet credit in the transaction is exact, and every transferred mint has retained quote membership.
- G2: the source owner holds a trust source.
- G3: every source is that owner's derived associated token account for the transfer's mint and program.
- G4: the owner is the single signing authority, any other signer is the fee payer, and the wallet has no role or account key. Since classifier v4 the wallet's key is tolerated only when it is neither a signer nor writable, a recognized associated-token-account creation unit in the transaction names the wallet as its owner seed, and every instruction referencing the wallet is such a unit's outer instruction or its own inner `initializeAccount3`.
- G5: production payout structure.
- G6: no contest, official-row contradiction, local revocation, published rotation gap or pending snapshot.

The trust sources are:

- `feed_witnessed_identity`: a supported, non-dirty exact-feed witness paying from its own derived account, with no time bound. It is primary when both sources apply.
- `published_withdraw_authority`: retained configuration snapshots. The nearest snapshot at or after the credit must name the owner, and so must the nearest snapshot before it. The snapshot is therefore taken after the payouts it covers.

Account derivation uses pinned `@noble/curves` and `@noble/hashes`. Addresses compare by exact value only, and batch size is recorded, not gated.

Ordinary quote transfers without positive origin evidence are unknown; absence from the capped feed cannot establish economic purpose. Failed, self/outgoing and wallet-participating transfers are excluded when established. Unsupported swap, claim, LP, mint/burn or airdrop structure cannot confirm; uncertain purpose stays explicit instead of guessed from logs or labels. No historical distributor address is a production trust entry.

### The native-SOL lane

A StonkFun reward can be paid in native SOL. A transaction with **no supported token transfer** is therefore not automatically without value, and the classifier evaluates its single placeholder row in this fixed order. Each row still carries exactly one branch's reasons.

1. `conflicting_evidence_quarantined`, then `failed_transaction`, then `wallet_participation`, exactly as before.
2. **The native-SOL lane (A2).** It is entered only when the transaction has no supported transfer, no wallet-owned token-balance row in either phase, and a trusted distributor identity — the same `feed_witnessed_identity` or `published_withdraw_authority` trust the token lane uses — is both the source of a decoded `system transfer` naming the wallet as destination and a signer of the transaction. Its gates are G1n the wallet's lamport delta equals exactly the System transfers naming it and the transaction moves no tokens; G2 trust, as the token lane; G3n one funding source, the identity's own system account, with no associated token account involved; G4n the owner signs, any other signer is the fee payer, and the wallet neither signs nor funds anything; G5 `payoutStructure` with the decoded lamport batch as the payout, so the System transfer positions are interpreted structure and their lamports are the expected movement; and G6, the token lane's conflict gate. A passing row is `attributed` with basis `distributor_pattern`, lane `native_sol` and the native-SOL sentinel as its mint, priced and reported under Attributed and never summed with verified. **A row that enters the lane and fails a gate is never excluded**: it stays `unknown_candidate` with `native_credit_from_distributor_unproven` followed by the failing gate's reasons.
3. `no_token_credit_to_wallet` (**excluded**), when the lane was not entered and neither balance array holds a wallet-owned row. The RPC emits a row for every token account a transaction touches, so their absence establishes that no token moved into or out of this wallet in any mint. Because the lane is checked first, this never excludes a lamport payout a trusted distributor funded and signed.
4. `zero_value_token_credit` (**excluded**), when every wallet-owned observation is an account provably created in this transaction, with no pre-balance row and a single post balance of zero. There is no positive credit under any rule.
5. `credit_without_supported_transfer_instruction` (**unknown**), for every other wallet-owned observation — chiefly `mintTo` issuance into a wallet-owned account. A mint is not a transfer from a distributor account and can satisfy no confirmation or attribution basis, but excluding it would assert that minted supply is never reward income, which this document settles the other way above.

## Durable representation and migrations

The Node 24 built-in `node:sqlite` `DatabaseSync` driver was tested on Windows/Node 24.18.0. It avoids native addon builds. Node labels this API release-candidate stability as of 24.15; use a compatible runtime. See [Node SQLite documentation](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html).

Schema version 7 uses STRICT tables, parameterized SQL, foreign keys, WAL, FULL synchronous commits and a five-second busy timeout. Creation and migrations run in `BEGIN IMMEDIATE` transactions. V1-to-v2 adds append-only metadata observations; v2-to-v3 backfills a transaction compatibility key and separates server cooldown from spacing. The old combined cooldown is carried forward conservatively as a server restriction. V3-to-v4 repairs missing classification invalidation, including databases already upgraded to v3. V4-to-v5 adds `withdrawal_authority_snapshots` (indexed by network and retrieval second) and the derived `identity_conflicts`, and it backfills snapshots from retained feed bodies. V5-to-v6 recomputes every retained normalization from the full transaction the row already holds — payout evidence revalidates a stored body by re-normalizing it, so a stale body would be refused — and rewrites only `body`; the primary key and the compatibility column derive from the raw transaction and are untouched. It then requeues **only** the signatures normalizer v2 can classify differently: those carrying an associated-token-account instruction at any position, or no supported transfer at all, which covers the lamport-only and `mintTo` shapes. Installing the classifier v4 marker inside that same block is what keeps the requeue targeted rather than network-wide, and the queue is drained to completion inside the same writable open, in batches that each commit on their own. Classifier versions otherwise use one-time markers on explicit writable opening (v2, then v3) to queue saved signatures for offline reclassification. Because the requeue is targeted, rows on untouched signatures keep classifier v3; the report treats v3 and v4 alike as tier-evaluating, which is sound exactly because the requeue covers every signature v4 can classify differently. V6-to-v7 only adds the empty `holding_sets` and `holdings` tables for holdings at refresh (below); no existing row changes, and a v6 database viewed read-only has no stored holdings. Read-only saved viewing accepts v4 to v7 without migrating or mutating data. Reopening is idempotent; newer unknown schema versions fail closed without deleting tables. Future changes require explicit versioned migrations. Credentials and authenticated URLs never enter a table.

Tables cover wallets/tracking starts, merged completed ranges, fenced leases, jobs and query checkpoints; deduplicated normalized transaction alternatives/provenance; per-signature feed alternatives; wallet watchers and pending classification work; individual classifications with raw quantities as TEXT; authority observations and supporting-signature dependencies; classifier versions; metadata; timestamped price history; cache freshness/completeness and provider cooldowns. Full transaction evidence is stored once per content hash, not repeated inside receipts. Retrieval provenance is retained separately. Conflicting alternatives remain append-only evidence.

Chain snapshots normalize with a neutral wallet context before storage. Classification derives participation/ownership separately for each searched wallet. The pure v1 grouping helper still treats different wallet contexts conservatively; the adapter never passes those different contexts as chain variants. The storage-only compatibility policy groups observations whose complete raw transactions differ solely by optional `transactionIndex`; it retains both original snapshots and provenance, presents the supplied index when consistent, and preserves both conflicting supplied indexes as alternatives. It never fills absent transfers/accounts or relaxes amount, ownership, signature, execution, instruction or other raw-evidence differences. Individual-credit identity v1 is unchanged. Evidence reads are signature-scoped (up to 16 reconciled transaction alternatives and 128 feed alternatives); overflow quarantines the signature while all originals remain stored. New content is normalized and the changed signature is revalidated by the pure reconciler. There is no lifetime evidence-state reload per refresh.

Contradictions invalidate confirmed rows and indexed dependents immediately in the evidence transaction. `#invalidateAttributed` runs in the same transaction as any of these writes:

- a new snapshot;
- a witness diff;
- new evidence on a signature carrying authority rows or an identity conflict;
- an `identity_conflicts` change;
- a local attribution revocation (`saveAttributionRevocation`, the counterpart of the historical revocation).

It demotes every attributed row with `attribution_recheck_pending` and queues every retained signature. A durable dirty queue recomputes authority/classification results. Reports cannot keep counting an affected receipt while reconciliation is pending. Dirty witnesses cannot support another candidate. Feed omission does not delete older evidence. Repeating older observations cannot clear a conflict. Automatic conflict adjudication and garbage collection are not implemented.

The v4 repair runs once in the migration transaction: it finds signatures with both indexed and unindexed observations in the same compatibility group, invalidates their saved confirmations and indexed dependents, and queues them plus retained transactions in their observed slots. Same-slot work recovers candidates whose old quarantine already removed their dependency edges. No evidence, provenance, coverage, job counter or request ledger is rewritten. Genuine differing indexes, missing transfers and changed transfers remain alternatives and remain quarantined after reconciliation. The migration does not clear quarantines or classify the entire history on startup; its version marker and durable queue commit together.

`processDirty` commits each batch's authority updates, classifications and queue acknowledgements atomically, even when called without an enclosing transaction. Exact-feed signatures are processed before candidates across batch boundaries so a candidate cannot finish while a required unchanged witness is still hidden as dirty. Interruption rolls back only the active batch; reopening resumes saved work without reseeding completed repairs.

`report` opens/migrates the database but only reads saved classifications. JSON `pendingClassification` gives exact network and watched-wallet pending signature counts; the human report shows both. Counts include pending authority evidence, not only receipt changes. Repaired results appear after `pnpm rewards reclassify <wallet> --db PATH` (offline, 100-signature atomic batches) or normal scan processing drains that work. `reclassify` processes network-wide pending support in the selected database and then reports the selected wallet, without loading credentials, fetching, advancing coverage or changing jobs/budgets. Existing exported report files stay unchanged; regenerate them after repair.

Reports use indexed batches of 500 classifications and bigint/decimal aggregation, not overlapping saved report totals or a lifetime transaction reload. They report classification-row counts, distinct-signature counts by status and overall, and counts by confirmation basis separately; one signature may have multiple rows or statuses. Detail output is limited to 500 records with a truncation flag; totals still include every unique retained receipt within the requested windows. The TypeScript report function accepts a different detail limit. UTC buckets contain days with confirmed receipts; an omitted day is not a verified zero.

Report `schemaVersion` 2 is additive. Existing counts, basis counts and windows stay verified-only. A `totals` block adds four separate groups:

- `verified` and `attributed`, each with its own windows and pricing coverage;
- `unknown`, with rows, signatures and proven wallet credits in token units;
- `unpriced`, with separate verified and attributed lists.

No field, CLI line or chart adds verified and attributed together. Attributed values are `null`, never 0, when saved rows predate classifier v3 or await an attribution recheck. Unknown proven credits are `null` when rows predate owner evidence.

Report `schemaVersion` 3 adds fields only (`priceRule`, `stalePriceSeconds`, the per-asset and per-window price fields below, and `history`); every v2 field keeps its meaning.

- **Price per mint.** Each mint is valued at its most recent saved observation that carries a USD value, from any job. A later observation without one (a missed lookup, such as a DAS fallback after a capped StonkFun budget) never hides it; `price` then holds the valued observation. A mint with no valued observation ever stays unpriced, and its `price` is its latest observation with that observation's reason. `RewardsStore.latestPrice` is the optional read behind this; a store without it values each mint at its latest observation only, as before.
- **Price times.** Each priced asset carries `priceAt` (the observation time, else the retrieval time), `priceAgeSeconds` (how long before the fixed cutoff it was taken, 0 when at or after it) and `priceStale`, true when that exceeds `stalePriceSeconds` (86,400). All three are `null` for an unpriced asset. A stale price stays in the USD figures at its saved value.
- **Per window.** `priceAges` gives the oldest and newest `priceAt` among the window's priced assets and `stalePricedMints`. The human report appends `STALE, <seconds> s before the cutoff` to a stale asset's line.
- **Loaded history.** `history` gives `floor`, `loadedFrom` (the oldest loaded day, the wallet's `trackingStart`), `oldestLoadedDay` (its UTC date), `notLoadedYet` (`{ startTime, endTime, days }` from the floor to it, or `null` at the floor), `earlierRemaining`, `nextBatch` (`{ startTime, endTime, days }` or `null`) and `lastBatch` (`kind` `first` or `earlier`, `startTime`, `endTime`, the `days` its job planned, `elapsedSeconds` and `finishedAt`, or `null`). Coverage gaps run from `loadedFrom` to the cutoff, so days not loaded yet are never gaps and never make `retrieval` partial. The human report prints them on one `History:` line. The dashboard's wallet report carries the same block.

## Jobs, checkpoints and budgets

Scanning is layered. `src/scanner/ranges.ts` sets the history floor, `HISTORY_FLOOR` (2026-08-01T00:00:00Z, moved from 2026-09-01 on 2026-09-24 to cover StonkFun since its launch in early August 2026), beside `FIRST_SCAN_DAYS` and `EARLIER_BATCH_DAYS` (both 7); nothing before the floor is ever requested, and a cutoff at or before it is refused. A wallet's loaded range runs from its oldest loaded day, `trackingStart`, to its newest coverage.

- **First scan.** A wallet with no coverage plans `max(floor, cutoff − 7 days)` to the cutoff, and that becomes its oldest loaded day.
- **Refresh**, the default job, plans only what is missing from the oldest loaded day to its new cutoff, including failed gaps inside the loaded range, and never anything earlier. A wallet already loaded from the floor, including one whose floor scan the previous build admitted, plans exactly as before. A wallet loaded from the old 2026-09-01 floor keeps its saved oldest loaded day and coverage; it now reports earlier history remaining, and its next Load earlier batch is 2026-08-25 → 2026-09-01.
- **Load earlier** (job kind `earlier`) plans the missing days of the seven days before the oldest loaded day, clipped at the floor. It keeps the saved cutoff and last sync. It is refused when nothing is loaded (`wallet_not_loaded`) or the loaded range already starts at the floor (`earlier_history_at_floor`). Only a completed batch moves the oldest loaded day back to the batch's start. An interrupted batch keeps its completed days, and the next Load earlier plans only that batch's missing days until it completes.
- **Check** (job kind `check`, the dashboard's Rescan dates, `{ kind: "check", startDay, endDay }` on the scans API) plans one range per chosen UTC day, at most `CHECK_MAX_DAYS` (7) whole days from 00:00 of the first to 00:00 after the last, each clipped to the loaded range. It keeps the saved cutoff and last sync, reads no StonkFun feed, hydrates nothing, requests no price and takes no holdings snapshot: it runs the range check below on every day and fetches only what is missing. More than seven days is refused (`check_range_too_long`, HTTP 400), as are days outside the loaded range (`check_range_outside_loaded`, 409), days that are not whole UTC days or run backwards (`check_range_invalid`, 400) and a wallet with nothing loaded (`wallet_not_loaded`). An unfinished check of other days is refused like another kind. It is complete once every day was checked, whatever the check found; a day whose listing still disagrees keeps its coverage and rows and is reported, not retried.

**Range check.** After a range's full read reaches its end (`paginationToken: null`), the engine lists the same query once more in signatures mode (`transactionDetails: "signatures"`, limit 1,000, every other field and filter unchanged, paginated), keeping succeeded signatures inside the range. A listed signature retained for another wallet is watched for this one; every other listed signature not saved is fetched in full mode with the same filters over the span from the earliest to the latest of them (`check-<range>-<page>` evidence), then saved, normalized and classified as usual. The two then agree when every listed signature is saved for the wallet and every saved succeeded history transaction the classification rows place in the range is listed; feed hydrations, which the query never lists, are not compared. Agreement completes the range and merges it into the wallet's `checked` ranges. Persistent disagreement leaves the range partial with the `check_disagreed` class: it is not coverage, its rows stay, and Resume or the next refresh reads it again from its start. A range whose read ended but whose check failed keeps `read: true` and a resume runs only the check. Each range records `check: { status, listed, alreadySaved, recovered, missing, unlisted }`, and a finished job `checkResult: { days, checkedDays, unconfirmedDays, newTransactions, newPayouts, alreadySaved, newVerified, verifiedAlreadySaved }`: attributed payout rows in transactions its checks saved and those already saved in its ranges, with verified rows counted apart and never added in. Ranges saved before the check existed are **read once**: they keep their rows and still count as loaded. Every check and refetch request counts in the job's Helius requests (and pages, for the refetch). The check adds one Helius request per day of up to 1,000 transactions, plus full-mode pages only when something was missing. Providers without a signatures listing read ranges once, as before. It exists because a full-mode read can end early with no pagination token and still look complete; a second listing of the same query catches it.

Missing intervals split into chunks of at most one day and overlap preceding coverage by at most 60 seconds, never reaching before the job's own start. A same-cutoff refresh reconciles only its last minute; a months-long absence plans the full gap. Coverage is never deleted, and touching completed ranges merge into one. A range that fails or stays incomplete remains a gap: the job pauses or exhausts with its completed days and rows kept, and a resume or the next job of its kind plans it again. Job completion uses the job's own target, its batch or the loaded range; report gaps use the loaded range. An unfinished job resumes by its id, and a new job of the other kind is refused while it is unfinished (`other_job_unfinished`). Each job records its `kind`, `batch`, summed run time and finish time, and a completed first scan or batch becomes the wallet's `lastBatch`. Planning and history progress count planned ranges as days. Delayed indexing beyond that overlap remains a provider limitation.

Each checkpoint includes exact wallet, start/end, page size, next cursor, durable page count, taint and restart count. A page's evidence, classification writes, cursor and terminal completed range commit atomically. Failed processing rolls back the whole page; replay deduplicates. Only explicit null pagination after every acknowledged page, and then an agreeing range check, completes a range. The client's `prefix_unverified` flag is resolved only by the adapter's same-query durable prefix, never by a last-seen timestamp. Excluded/uncertain page evidence taints the range and stays retained.

Cursor invalidation/loops allow one restart of that bounded day on a later resume, using the same counters/deadline. Older failed ranges remain visible while newer chunks may complete. The client also detects loops within an invocation. Cancellation/process exit preserve committed work. A SQLite wallet lease lasts 120 seconds and renews during work. Local mutations are synchronous; a worker that loses its lease cannot overwrite a successor's job. Explicit resume preserves cutoff and limits. `scan` resumes an active/paused refresh first; another scan after completion advances the cutoff. `scan --earlier` loads one batch, resuming an unfinished one first. A new user-triggered job after exhaustion plans outstanding gaps.

Default limits are 200 Helius requests, 200 validated fetched pages, 10 executions including resumes, and a 60-minute absolute deadline. The StonkFun budget is sized for the CLI (without `--max-stonkfun`) and every dashboard scan: the job starts with a cap of 200, and when pricing starts the limit becomes the requests already made (discovery) plus one per mint without a saved unexpired price, never more than the cap. A resume keeps the original job's choice and cap, recorded under the `stonkfun-budget:<job>` cache key. Retries draw on the same budget, so a retried price can leave the last mint to the DAS fallback. `--max-stonkfun N` fixes the budget instead. The CLI prints the requests used against each limit after `scan` and `scan --earlier`, then any failure class and, for a job that stopped short, `Completed days are saved: <n> of <planned>.` The dashboard's job status shows the same counts as `requests: { helius, stonkfun }`. Every HTTP dispatch reserves a durable request before sending; crashes may conservatively overcount, never undercount. A fetched page consumes budget even if its evidence transaction fails.

Each provider has one token bucket: by default Helius 8 requests per second with a burst of 10, and StonkFun 4 with a burst of 5, set by flag or `SCANNER_*` environment name (`pnpm rewards --help`). The bucket lives in the provider's `cooldowns.until` value as its theoretical arrival time, so every stage and every process using the same database shares it, and a request dispatches at once while the bucket holds a token. Server restrictions are persisted separately in `server_until` and hold back the whole provider: a Retry-After, an exhausted reset header, and for an HTTP 429 or JSON-RPC rate-limit error without Retry-After the provider's own backoff over its consecutive rate limits. `reserveDispatch` admits only at the current time or returns a next-check time without taking a future token. Every waiter rechecks the bucket and the server cooldown in the atomic admission/request-budget transaction, and only an admitted dispatch takes a token. No transaction spans an asynchronous sleep. Cancellation, deadlines, exhausted budgets/allowances and a cooldown beyond 60 seconds refuse before dispatch without consuming a request, and a refusal is never retried; failed accounting takes no token. Cooldowns are recorded at header arrival and survive body failure. Helius DAS calls — `getAssetsByOwner` and the `getAsset` price fallback — take their tokens from a separate `helius-das` bucket at 2 per second with no burst (Helius's free-plan DAS limit), after any Helius server cooldown, and still count against the job's Helius budget.

History pages, registry reads, prices, hydrations and DAS lookups retry a rate limit, a 5xx, a network failure or a timeout up to three times. Backoff is 1 s, 2 s, 4 s … capped at 30 s, stretched by up to 25 % jitter; a server's Retry-After replaces it. Each retry is a request against the budget. A provider cooldown is waited out before an attempt's timeout starts. Every wait — pacing, rate limit or retry — reaches job progress as waiting for the provider with its reason, and the CLI prints it. Retained registry sources keep the existing failure codes. Observers cannot control retrieval success.

Failure classes (`src/scanner/failures.ts`) come from responses the clients already handle. Each job keeps its latest as `failure: { class, message, detail? }`, cleared on resume:

- `key_rejected`: a Helius authentication failure.
- `helius_rate_limited`: an HTTP 429 or JSON-RPC rate limit that outlasted its retries. It is temporary, not a failure; a running dashboard job also shows it live while it waits one out.
- `helius_quota`: a plan, entitlement or HTTP 403 refusal, with Helius's own message as `detail`.
- `stonkfun_unreachable`: every registry request failed on the network, a timeout or HTTP. History still loads.
- `network`: a Helius request that failed in the network or timed out.
- `check_disagreed`: a range's full read and its signatures listing still disagree after the missing span was fetched again. The range stays partial; Resume or Refresh reads it again.
- `other`: anything unrecognized, with the raw message as `detail`.

Provider text is kept only for the quota and other classes: printable characters, with URLs, UUID-shaped keys and key or token assignments redacted, cut to 300 characters, and dropped entirely if it still reflects the key. A rejected key or a quota refusal stops the job after the first refused day. Cancellation, spent budgets and the deadline have no class.

Independent provider work runs through a bounded pool under the limiter, 4 in flight by default (`--concurrency`, `SCANNER_CONCURRENCY`, 1–16): the feed hydrations and the per-mint price lookups, each a StonkFun read with its DAS fallback. Results are saved strictly in feed or mint order, each as soon as every earlier one is saved, so the evidence written equals the serial loop's whatever order responses arrive in. Admission keeps the serial checks: a saved unexpired price is reused, and once the budgets are spent no further lookup starts. Cancellation starts nothing further and discards results not yet saved. History pages stay sequential because each needs the previous cursor. Registry reads stay sequential too: their retrieval ids are assigned in request order and are part of retained feed evidence. There is no separate per-transaction or per-mint metadata request to parallelize — history pages carry full transactions and token metadata arrives with `/pairs`.

Same-slot lookups (a new transaction, feed row or authority change requeues its slot's retained signatures) name the v1 `transaction_slot` index. Without planner statistics SQLite otherwise answered them from the primary key's network prefix, parsing every retained body per lookup.

The special live-verification mode additionally uses a persistent milestone allowance of 5 public and 30 Helius requests across jobs for the supplied validation wallet. Its database must be preserved throughout the task. This is an implementation-verification mechanism, not a production entitlement. Ordinary standalone use has no hosted refresh allowance.

## Provider freshness and prices

Default discovery requests one launch page, rewards summaries/recent rows, pairs, and one `/launchlab/pricing?quoteMint=<USDC>` configuration read per job. A successful read is retained as a withdraw-authority snapshot, even when the feed has no rows. It is never payout verification. Within 24 hours, later jobs refresh rewards without recrawling launches/pairs. `--catalogue-pages` opts into another bounded sweep. Discovery stays incomplete (the CLI does not run the loader's full stable-snapshot catch-up). Previously observed quote membership persists, while metadata refresh preserves absent fields. Reward summaries/feed mints extend the universe; pairs alone cannot authorize a quote.

Holdings at refresh: a dashboard refresh or CLI scan that completes (no coverage gap left) reads the wallet's fungible holdings with `getAssetsByOwner` before its checkpoint, 1000 a page, every page, keeping each positive balance's mint, exact raw balance (a JSON number's source text, so no digit is lost), decimals, and on-chain name and symbol. In the same step it computes what the retained transactions show the wallet holding, per mint, and stores both with the retained-data fingerprint as one set in `holding_sets` and `holdings`. A paused, exhausted or failed scan makes no DAS call and stores nothing; a snapshot page that cannot be read stores the history rows only, and readers keep the last complete snapshot. Every set is kept.

Wallet history runs before hydration to reuse full saved transactions. At most 12 feed signatures are hydrated per job. Provider absence, malformed responses or exhausted budgets remain partial; no historical feed is invented. New jobs refresh distribution evidence. Failed ancillary stages do not retry without bound; a new user-triggered scan can refresh them.

Pricing covers verified mints first and attributed mints only with the remaining shared budget; a sized budget leaves room for every one of them. StonkFun identity and `quoteUsd`/observation time are validated first. Quotes older than one hour or more than 60 seconds in the future are rejected; accepted prices cache for at most five minutes and never beyond that freshness horizon. DAS validates exact asset identity, USD currency and a finite nonnegative decimal price. Its observation time stays null with an explicit possible 600-second upstream cache caveat; local caching is at most 600 seconds. Missing-price results cache for one minute. No stablecoin symbol or missing data supplies a dollar price. Saved reports retain timestamps/expiry and warn that prices may be stale; viewing does not refresh them. Reports value each mint at its most recent valued observation and flag one taken more than 24 hours before the cutoff as stale (report schema v3, above).

Valuation parses decimal/scientific strings into bigint coefficients/scales. Raw token amounts never convert to Number. USD aggregates round half up to six decimal places at output, with `/7` before rounding for the rolling daily average. Null USD means no priced confirmed amount, not zero; priced totals exclude explicitly listed unpriced quantities. Repricing never creates a receipt.

## Remaining scope

The implemented local dashboard calls the engine directly; [DASHBOARD.md](DASHBOARD.md) documents its loopback API, read-only saved viewing and browser job lifetime. Reports additionally expose unknown-only reason counts and each asset's latest reward time/signature for presentation, without changing classification or totals. The optional read-only SQLite constructor accepts schema v4 to v7, never runs migrations, and fails closed on a newer schema; writable/CLI behavior is unchanged.

The scanner is local only: no hosted authentication, queue, publication or deployment is part of it. Every scan uses the user's own Helius key.

# Local rewards dashboard

Double-click **Start Rewards Dashboard.cmd** on Windows, or run `sh start.sh` on Mac or Linux, after installing Node 24.15+. Both check Node first, then run `scripts/launch.mjs`: it enables pnpm through Corepack when pnpm is missing (or runs it through Corepack where enabling needs administrator rights), runs `pnpm install --frozen-lockfile` when `node_modules` is missing or the lockfile's SHA-256 differs from the one it saved after the last install, checks the port, and then builds the dashboard, starts the loopback server and opens the browser. When the port already serves this dashboard it opens that instead. Each failure prints one plain message with what to do next. `--check` runs the checks and exits without installing or starting anything. Keep the window open during scans. Closing the server preserves acknowledged work; an interrupted job needs explicit Resume, subject to the existing two-minute lease and saved budget/deadline.

```powershell
pnpm rewards:web
pnpm rewards:web -- --no-open
pnpm rewards:web -- --no-open --offline --db .cache/example.sqlite --port 4319
```

Default URL: `http://127.0.0.1:4317`. Default storage is the existing `stonkfun-rewards/scanner.sqlite` in local application data. `--db` and `--port` are server startup options; the browser cannot choose filesystem paths. There is no automatic scan. Paste or type a public wallet address, or select a saved wallet; either becomes the wallet in view at once. The last tracked wallet in view is remembered in this origin's local storage and opens next time while it is still saved; a first launch with no saved wallet focuses the empty wallet box. **Scan wallet**, for a wallet with no saved coverage, or **Refresh rewards** explicitly starts a real scan of the wallet in view with a key entered in the page, or else `HELIUS_API_KEY` from the process or the ignored `.env`. Do not use real scans during offline verification. A running server reads its built files once at startup, so it shows a rebuilt dashboard only after a restart. The speed flags `--helius-rps`, `--helius-burst`, `--stonkfun-rps`, `--stonkfun-burst` and `--concurrency`, and their `SCANNER_*` environment names, apply to dashboard scans as to the CLI (README).

The provider indicator, in the status panel, reports only configured/not configured, with a “checked only when scanning” qualifier until an explicit scan/resume checks configuration or a key is entered. Startup, health, wallet listing, saved reports, progress and local reclassification do not inspect credentials. A present `.env` is not treated as proof of a usable provider. `--offline` disables all work mutations, including local reclassification and key entry, for review sessions.

### Entering the Helius key in the page

When a scan or refresh finds no provider, the page opens a small form under the primary button: a masked key field, **Remember on this computer** (off by default) and **Save**. The page checks the key's shape (8–256 letters, digits, dots, dashes or underscores, which Helius's UUID-shaped keys satisfy), posts it once to `POST /api/v1/provider-key` under the same Host and Origin checks as every mutation, then clears the field. The browser stores nothing. `src/web/key.ts` keeps the key in the server's memory for its lifetime and uses it for every later scan ahead of the environment. With Remember set it also writes `HELIUS_API_KEY=<key>` into the ignored `.env` in the server's working folder, which the launcher sets to the scanner folder. That write keeps every other line, replaces an older key line, and swaps the file in with one rename. A failed write keeps nothing and answers `key_not_saved`. The answer is the health record, now configured; the key is never logged, never returned, and never written into a report, database or review package.

## Architecture and adapter boundary

- `web/`: React/TypeScript presentation built by Vite. Plain CSS and accessible SVG; no chart library, CDN, remote fonts or image fetches. Client imports from server files are type-only. `web/model.ts` formats exact strings and compares quantities and USD as exact decimal strings. It also adds the report's USD day buckets and divides them by whole days with BigInt, rounding half up to six places as the report does. It shows USD to two decimals, rounded half up from the exact string with BigInt, with thousands separators, and "<$0.01" for any positive value under one cent; the evidence modal and the two exact chart data tables keep the report's full precision. Only chart geometry and the relative bars beside exact figures use numeric approximations of already aggregated USD strings. `App.tsx` is the shell. `Status.tsx` is the header status control and its panel; `Refresh.tsx` is the primary button (Scan wallet or Refresh rewards) with Rescan dates beside it, the loaded-history line with its Load earlier button, the not-scanned panel and the key form; `Rescan.tsx` is the Rescan dates dialog. `Hero.tsx` holds the period figures and each group's explanation, which the status panel reuses. `Tabs.tsx`, `Overview.tsx` with `Chart.tsx` (the period panel and its control), `Tokens.tsx`, `Payouts.tsx`, `Trust.tsx` and `Coverage.tsx` are the five tabs. `Sheet.tsx` holds the dialog sheet, the full-address row and the copy button; `Progress.tsx` is the scan dialog.
- `src/web/server.ts`: Node HTTP and static adapter. One origin serves the production frontend and `/api/v1`. No Vite development server or CORS service is exposed.
- `src/web/service.ts`: local job lifetime and admission adapter. Calls `runScan`, `processDirty`, and `buildReport` directly. Does not invoke CLI subprocesses or duplicate classification. Provider factory, store, clock and cancellation are injected. It builds reports with every detail record, so the token details, receipts and trust identities cover every attributed row rather than only those inside the first 500 records. `sources(wallet)` gathers the saved data behind the likely source launches inside one read transaction. A refresh stores the wallet's history-derived holdings with the retained-data fingerprint they came from, and its holdings snapshot ([SCANNER.md](SCANNER.md)). While that fingerprint still matches — watched signatures, retained bodies and metadata observations are unchanged — the endpoint reads those small rows. Otherwise, and for a wallet not refreshed since holdings were stored, it reads the token balances from every retained transaction body the wallet watches, which on the saved wallet meant 711 MB of JSON and 3.4 s. It keeps the holdings, and each quote mint's summary launches, per wallet until the fingerprint or the stored set changes.
- `src/web/view.ts`: explicit browser projection. Omits raw transaction objects, provider errors, source configuration, authenticated URLs, caches and database paths. Known reason codes and fixed Solscan links are projected separately. It projects the schema-v2 groups — the verified and attributed group wording, a recheck-pending count, per-mint trust sources — and, additively for this layout, `attribution.dayTokens` (the report's own per-day, per-mint buckets), `attribution.receipts` (every attributed row newest first, up to 10,000, each with its full evidence and its exact amount at the mint's saved current price, with `receiptsComplete`), `attribution.tokenDetails` (each token's listed receipt ids and first receipt time), `attribution.identities` (each sending identity with its trust sources, counts, witness span and snapshot times), `attribution.conflicts` (rows refused for a conflicted or revoked identity) and `excludedReasons`. Every attributed projection is `null` while the tier is not evaluated, and the detail-derived ones are `null` rather than partial when a caller truncates the report. The earlier `attributedEvidence` list, bounded to 500 rows, stays in the DTO unchanged; the page now reads `attribution.receipts`. The unknown and confirmed samples keep their bound of the first 500 detail records. From report schema v3 every priced asset, in both groups and in each day token, also carries `priceAt`, `priceAgeSeconds` and `priceStale`, each window summary its `priceAges`, and each day token its `mintAddress` for Copy CA. `sourcesView(report, retained)` is a separate projection behind its own endpoint. It gives each verified and attributed token its likely and exact source launches and every summary launch (`launches`, with names only where known), with `holdingsAt` and `holdingsSource`, computed only from saved data passed in: summaries, history-derived holdings, the stored snapshot, launch metadata and feed rows.
- `src/web/main.ts`: local runtime configuration. Opens existing schema-v4, v5 or v6 saved data read-only, using read transactions without migrations; a newer schema fails closed. A missing database shows an empty local view; it is created only on explicit work. An older schema needs a deliberate existing CLI migration path. The connection becomes writable only for a user scan, resume or reclassification.
- `scripts/start-dashboard.mjs`: build/start/open wrapper. Only the launcher runs build subprocesses; web requests invoke the engine in-process. `scripts/launch.mjs` runs the first-run checks for `Start Rewards Dashboard.cmd` and `start.sh` before it; a busy port at server start reads "its port is already in use".

The framework-independent scanner and `Providers` remain unchanged interfaces; `RewardsStore` gains one optional read, `latestPrice`, which the report uses when a mint's latest saved observation carries no value ([SCANNER.md](SCANNER.md)). Another adapter can replace local SQLite, providers and job admission while keeping the reward logic and the browser DTO. Optional `listWallets` and `rewardSummaryLaunches` belong to the local adapter, and `RewardsStore` gains the optional `walletTokenBalances`, `retainedFingerprint`, `saveHoldings` and `holdings`; without the retained-launch reads the sources endpoint answers `null`, never an empty list. No hosted authentication, shared hosted scheduler or deployment is implemented.

Registry schemas and retained fixtures contain no validated image URI. Token avatars are deterministic SVGs derived from canonical mint addresses. `Avatar` is the replaceable presentation boundary for a future validated metadata service; no metadata or images were invented or fetched.

## Page structure

The page is one screen per section: on a desktop no tab needs more than one viewport of scrolling, because long lists scroll inside their own panels.

- **Header** (sticky on desktop): the wallet box, placeholder "Paste a Solana wallet address", with the saved-wallet selector; the primary button, which for a scanned wallet has "Last refresh <UTC>" and the loaded history beneath it, both in its accessible description; and the **Status** control. Nothing sits between the header and the tabs.
  - **Wallet in view.** The wallet box and the saved list choose one wallet in view, and every button acts on it. A well-formed address, trimmed, switches the view as it is pasted or typed; Enter does the same, and choosing a saved wallet fills the box with it. Switching reads the wallet's job and report and nothing else. A wallet the server does not track is simply not scanned yet, not an error. A wallet joins the saved list once its report has saved coverage, so after its first scan.
  - **Wallet address.** An address that cannot become the view stays in the box: Enter or the primary button then shows its reason inline under the field (an empty field, a character outside base58 — 0, O, I, l or punctuation — or a length outside 32 to 44), marks it invalid and sends no request; typing clears it. No button starts a job for it.
  - **Primary button.** **Scan wallet** for a wallet with no saved coverage (no completed day and no finished sync), **Refresh rewards** for one with. Its second line names the UTC time the scan reads: "Checks <last cutoff> UTC → now" for a refresh, from the earliest gap instead when the loaded range has one; "Scans <day> → today (7 days)" for a first scan; and while this wallet's job runs, "Scanning <start> → <end>", both times to the minute when the span is under a day. It is disabled while this wallet's scan runs ("Scan running…"), on an `--offline` server ("Offline · scan disabled" or "Offline · refresh disabled"), and while another wallet's job runs on this server, with "A scan is running for <short address>" beneath it; the view can still switch then. With no provider configured it opens the key form described above.
  - **Not scanned yet.** A wallet with no saved coverage shows one panel in place of every tab's content: "<short address> has not been scanned yet.", a Scan wallet button that waits as the header's does, and "The first scan covers the last 7 days and takes a minute or two. Older history loads afterwards in 7-day batches." When its first scan saves its days, the page reads the report and shows it.
  - **First launch.** With no saved wallet the wallet box is empty and focused, the page welcomes with "Start with a wallet address.", and the primary button reads Scan wallet and explains the empty box.
  - **Loaded history.** From the report's `history` block. While earlier history remains it reads "Loaded <oldest loaded day> → today · N days left to <floor, as Aug 1>" with a **Load earlier history** button whose second line names the batch, "Loads <batch start> → <batch end>"; at the floor it reads "Full history since <floor day, 2026-08-01>" and has no button. Every floor date on the dashboard comes from `HISTORY_FLOOR`. When saved coverage already holds days of the next batch (an interrupted batch), the button reads **Continue loading** beside "n of 7 days saved". The button is disabled when the primary button is. It starts a Load earlier job through `POST /api/v1/scans` with `kind: "earlier"` (resuming an unfinished Load earlier job that can resume, so its saved days are kept) and opens the same progress dialog as Refresh.
  - **Rescan dates**, beside Refresh rewards for a scanned wallet and disabled when it is, reads "Rescan dates · N days to check" while any loaded day is Read once or partly not loaded, and "Rescan dates" alone once every loaded day is Checked. It opens a dialog listing each calendar week (Monday to Sunday, UTC) holding a loaded day, clipped to the loaded days, in two sections, each newest first. **To check** holds every week with a day not checked yet, labelled with the count ("2026-09-14 → 2026-09-20 · 3 days to check"), and picks one on click; with none it reads "Every loaded day is checked." **Already confirmed** holds every week whose days are all Checked, shaded grey, disabled and `aria-disabled` ("2026-09-07 → 2026-09-13 · confirmed"), or "No week is fully checked yet." **Check other dates**, collapsed, holds start and end day fields bounded to the loaded days, for checking any days again, confirmed or not. The dialog opens on the first week to check, or on the week Coverage named; with nothing to check and nothing chosen, Rescan stays disabled. A choice longer than seven days ("Rescan at most 7 days at a time; this is 8."), outside the loaded days, backwards or not a real date shows its reason and cannot start. Before starting it names the exact range: "Rescan 2026-09-14 → 2026-09-20 (7 days). Checks these days again and adds anything missed. Payouts already saved are not counted twice." **Rescan** starts a check job (`kind: "check"` with `startDay` and `endDay`, [SCANNER.md](SCANNER.md)) and opens the progress dialog, titled "Rescanning <start> → <end>", with its days, "n of m days done" and the request counts. Once finished its top line reads "Rescanned <start> → <end>: N new payouts found, M already saved.", attributed payouts from the job's `checkResult`; verified ones, if any, follow as their own sentence, never added in; a day Helius still listed differently is named with a suggestion to rescan it later, and when every day of the range agreed the line ends "Every day in this range is now checked."
  - **Status** shows the short address of the wallet in view, the job's state (WORKING with the day being read, "WORKING · 2026-09-17", then COMPLETE, PAUSED, EXHAUSTED, or NO SCAN), a SYNTHETIC or OFFLINE tag when they apply, and the last refresh. A wallet with no saved coverage reads "Not scanned yet", with no last refresh, except WORKING while its first scan runs. It opens a panel, closed by Escape, the button or a click elsewhere, that holds only what no period governs. The panel shows the mode (local and read-only, or offline viewing), the provider indicator, the last sync and the fixed cutoff. It shows the job with its elapsed time, its phase, and "finished <UTC time>" once the job has finished or else how long ago it last reported ("last activity 5s ago"), a stopped job's failure message and saved days, the last job's kind (Refresh, First scan, or Load earlier with its days), its elapsed time and its Helius and StonkFun requests, **View scan progress**, which opens the progress dialog (whose meta line reads "Finished <UTC time>" the same way), and the requests the job used against each limit (StonkFun, Helius, history pages). Another wallet's running scan appears here with a way to its progress. Last come one row each for **Verified**, **Unknown · not counted**, **Excluded** and **Unpriced · excluded from USD** (verified and attributed counts apart), each opening onto the report's fixed explanation and exact counts. The verified row holds the verified group's own three USD figures and confirmation basis counts. Excluded rows have no report group, so that row carries the status name, its counts and each exclusion reason with its plain one-line explanation. Errors show under the tabs.
- **Tabs**: Overview, Tokens, Payouts, Trust, Coverage, with one roving tab stop (arrow keys, Home, End). The route lives in the URL hash, so refresh, Back and shared links keep the tab, its filters and the period:
  - `#overview?period=7d|14d|30d|60d|90d|all`, or `#overview?period=custom&from=YYYY-MM-DD&to=YYYY-MM-DD`;
  - `#tokens`, or `#tokens?token=MINT:DECIMALS` for an open token;
  - `#payouts?day=YYYY-MM-DD&token=…&trust=…&price=priced|unpriced`.

  Unknown tabs read as the overview, and unknown or malformed parameters are dropped. Another tab opens unfiltered. Selecting the open tab again keeps its filters, and the Overview tab returns with the period it last showed. Loading another wallet clears the filters and the period and keeps the tab.
- **Overview**: one panel for the selected period — its figures, the attributed daily chart, the period's token ranking and verified. The Tokens and Payouts tabs follow no period.
  - **Empty loaded range.** When the attributed tier is evaluated and the loaded range holds no verified or attributed payout, one panel replaces the chart: "No StonkFun payouts found between <oldest loaded day> and today." with Load earlier history while earlier history remains, or "No StonkFun payouts found since 2026-08-01." at the floor, which adds that rows the scanner could not attribute are counted apart in Coverage. An empty chart never shows without it.
  - **Figures.** The panel leads with the attributed priced USD for the period as the only large figure, under the label **Attributed**; the dashboard shows no "not verified" wording anywhere, while the report's own label and the CLI keep theirs. The tier's explanation ("Paid from a trusted StonkFun distributor…") is the first line of the figure's (i) popover, not a line under the daily chart. Beneath it is the period's exact UTC range ("2026-09-16 → 2026-09-22 · 7 days"). Beside it are the period's payouts, tokens, daily average and unpriced receipts, which the report's **Unpriced · excluded from USD** label heads and which are never valued.
  - **Period control.** 7D, 14D, 30D, 60D, 90D, ALL and Custom sit at the panel's top right. A fixed period ends on the cutoff's UTC day and covers exactly that many calendar days. It stays disabled until tracked history covers every one of its days. Its tooltip says "Load earlier history to enable" while earlier history remains and the days back to the floor would cover it, and "needs N days of tracked history" otherwise; it is still focusable, and its reason is also its accessible description. ALL runs from the first tracked day. Custom opens two UTC date inputs bounded to tracked history, starting from the range on screen; an invalid range (an end before its start, a day outside tracked history, or no real date) shows its reason and changes nothing. With no period in the hash the overview shows 7D, or ALL while tracked history is shorter than seven days. A linked period that tracked history cannot cover falls back to that default and says why.
  - **Info button.** It carries the group's explanation and how period figures are made. It gives the report's own rolling-168-hour figure, its daily average and the since-tracking-start figure for reference. Then comes when the period's saved prices were taken (oldest → newest) and each token whose price the report flags stale, as "stale · <age>" with its price time. Last come the trust-source badges and the valuation caveat.
  - **Not evaluated** and **Rechecking** take the large figure's place, with their detail instead of the range and small figures, so no attributed figure reads 0.
  - **Charts.** The attributed daily chart draws exactly the period's calendar days at its measured pixel width. Its day labels thin out as a period grows so they never overlap. Its left scale steps in round values from zero, each step 1, 2, 2.5, 4 or 5 times a power of ten and the smallest that reaches the highest day in at most four steps (a $1,500 day reads 0, 400, 800, 1.2K, 1.6K); bars are drawn against the top tick, and the verified chart scales the same way. Each day's bar is split by token USD share.
    - **Colors.** The selected period's twelve tokens with the highest priced USD take twelve fixed colors in rank order. The first eight are the data-viz reference palette's dark steps. Slots nine to twelve, cyan `#08a4bd`, brown `#945701`, fuchsia `#a519cb` and olive `#838503`, were chosen one per missing hue family. They pass the same checks as one set against this chart surface (`#0b131b`): OKLCH lightness 0.48–0.67, chroma ≥ 0.10, adjacent colour-blind ΔE ≥ 8 (worst 8.4, unchanged), adjacent normal-vision ΔE ≥ 15 (worst 19.3), and 3:1 contrast. Every other priced token shares one gray **Other** segment. A legend above the plot names them.
    - **Stack.** Segments stack from the baseline in legend order with a 2px surface gap. The Other segment's value is the day's report total less the named tokens, so each bar ends exactly at the day's total. Unpriced receipts never enter a bar.
    - **Tooltip.** Each day with receipts is a focusable control; hovering or focusing it opens a tooltip right beside that day's bar.
      - **Placement.** Its near edge sits 8 px from the bar: to the right, or to the left only when the right would overflow the chart. It may cover neighbouring days. Only a chart too narrow for either side gives it the roomier side, at least 220 px wide and inside the chart. It starts at the canvas's top, at most the plot's height, and its top is clamped inside the viewport (below the sticky header, 8 px from each edge) as the page scrolls or the tooltip grows. Pinned tooltips use the same placement; on a phone a tap still pins a bottom sheet. It takes the pointer, and its token list scrolls inside it when the day holds more rows than the plot's height.
      - **Grace.** Hover follows the pointer over the plot. Column hover pauses while the pointer is inside the tooltip, so a day it covers never takes over. It also pauses while the pointer crosses from the bar to the tooltip: through the 8 px gap, or beside the bar under the tooltip, since a short bar's pointer reaches the tooltip on a diagonal. There the 150 ms grace decides, restarted only while the pointer is still closing in; resting 150 ms opens the column under the pointer instead. The tooltip stays open while hovered, and closes 150 ms after the pointer leaves both it and the chart.
      - **Content.** It gives the day's report total, its receipts, the unpriced receipts and tokens left out of the bar, and a link to all of the day's payouts. Then one row per segment: line key, ticker, share, USD, exact amount and a **Copy CA** button that copies the full mint and shows Copied (the native-SOL sentinel says it has no mint address). A ticker opens Payouts filtered to that day and token. **Other** shows its share, USD and receipt count and expands to its own tokens in the same rows, their shares apportioned to add up exactly to Other's. Shares are rounded by largest remainder so they sum to exactly 100.0%.
      - **Order.** Rows are sorted by exact USD, highest first. A **USD** header above the list, with an arrow for the direction, flips it to lowest first and back. Other, a remainder rather than a token, follows the named tokens either way, and its expanded tokens follow the same direction; an unpriced row always sits last. Equal USD falls back to the symbol. The direction is kept in session storage, so it holds from day to day, across tabs and reloads, on hover, pinned and on the phone sheet.
    - **Highlight and navigation.** Hovering a segment or a legend entry dims every other token across the chart; on a focused day the arrow keys choose a token, and Enter opens Payouts for that day and token, or the day alone without one. A click on a column or a segment pins the day, lighting the segment clicked; a click on another segment of a pinned day moves the light, and the same click again unpins it. Escape or a click elsewhere closes a pinned day. A day's axis label opens the day alone.
    - **Palette scope.** Within a period the colors never move, and the same token keeps its color in the tooltip, the Tokens table and drawer, and the Payouts rows and banner, all following the overview's period. The exact-data table lists each day's split by token.
    - **Tokens you were paid in.** Directly under the daily chart, titled with the active period ("Tokens you were paid in / 7D · 2026-09-15 → 2026-09-21") and one line: "Ranked by USD at current prices. A payout does not name the launch it came from, so this ranks reward tokens, not launches." It follows the period control (7D to 90D, ALL, Custom) and is computed only from the report's day buckets already loaded, with no request of its own.
      - **Rows.** Horizontal bars, one per token: each token's USD is the exact sum of its day values in the period and its receipts are counted the same way. By default the top twelve by USD are listed, in the same order and colors as the daily chart's legend, and every other priced token folds into one gray **Other** row with its token and receipt counts. **Show all N tokens** (N counts every token in the period, unpriced ones too) lists every priced token, those past the twelfth in Other's gray, and **Show the top 12 and Other** folds them again. Each row gives the ticker, the bar (relative length only, against the longest row), USD, its share of the period's priced total and its receipts, with **Copy CA** for the full mint. Shares are rounded by largest remainder so the listed rows sum to exactly 100.0%; the total is the sum of the listed tokens' values, which can differ from the period figure only in its sixth place.
      - **Order.** Highest USD first; the **USD** header, with an arrow, flips it to lowest first and back. Other follows the named tokens either way.
      - **Unpriced.** Unpriced tokens follow the bars, most receipts first, marked UNPRICED with no bar and no share, their receipts counted.
      - **Tickers.** A ticker opens Payouts filtered to that token and sorted by USD, highest first (`#payouts?token=…&sort=usd-desc`). Payouts has no date-range filter, so the period does not carry over.
      - **Phone.** Each row stacks across the full width: ticker and USD, the bar on its own line, then share, receipts and Copy CA; only the USD header shows, as a chip.
    - **Verified.** The verified chart follows beneath it on the same days while verified has rows; with no verified row it is left out entirely, as is the Tokens tab's verified table, with no note in its place.
- **Tokens**: the attributed tokens in a compact table — symbol and name, exact quantity, USD, receipts, last receipt, trust chips, priced or unpriced — with a search box (symbol, name or mint) and exact sorting on every column but trust and price; unpriced tokens stay after priced ones in both USD directions. A token priced from a stale saved price reads "stale · <age>" under its PRICED badge, and its USD cell's title gives the price time. A row opens a side drawer: the full mint with a copy button and a Solscan link, quantity and USD, first and last receipt, the saved price time (with "stale · <age>" when flagged), each trust source with the report's fixed explanation, and that token's receipts newest first (date, amount, USD, sender abbreviated with its full address on hover, evidence link, and a date that opens the receipt's evidence). The verified token table, or its one-line note, follows in its own panel.
  - **Likely source launches.** A chevron at the start of each row, in both tables, expands the row to **Launches you hold that pay in $SYMBOL**. Under the heading, "Holdings as of <UTC time>" gives the stored snapshot's time; a wallet not refreshed since snapshots were stored reads the time of the latest retained transaction behind its holdings, with a hint to refresh. Then the fixed line: "The payout itself does not name its launch. These are launches this wallet holds, or held earlier, whose rewards are paid in $SYMBOL."
    - **Which launches.** Reward-mode launches whose retained /rewards summary names the token as its quote mint (every retained read, not only the latest), intersected with the launches in the last refresh's snapshot and the launches the wallet's retained transactions show it holding at some point. A launch held since before tracking started appears through the snapshot.
    - **Each launch.** Its symbol and name from retained metadata or the snapshot's on-chain metadata, or else its short address; Copy CA, a StonkFun link to its token page (`https://www.stonkfun.xyz/token/<mint>`) and Solscan. **Holding now** when the snapshot holds it (with the snapshot's amount) or, without a snapshot as recent as its last trade, when its transactions end with a balance; otherwise **Held earlier, sold**, with its last trade and transaction. Holding-now launches come first.
    - **Exact.** A verified token's launches that the official feed names for its confirmed receipts are listed apart under **Named by the official feed · exact**, and never repeated as likely.
    - **Nothing matched.** "No launch you hold was found that pays in $SYMBOL.", and one line on why: a launch held and sold before tracking started, or a paying launch missing from StonkFun's summaries. A token no retained summary names says that instead of offering a list.
    - **Full list.** Under the matches or the empty message, **Show all N launches that pay in $SYMBOL** opens every launch the summaries name, named ones first, 25 a page, each with its name when known, short address, Copy CA and StonkFun link.
    - **Loading.** The page reads the sources endpoint as soon as the Tokens tab opens, once per report, so a row expands straight onto its launches, and a reload keeps the last ones on screen. With nothing to show yet it reads "Checking launches you hold…"; after 15 seconds or on an error, a short message and **Retry**. The chevron never opens the drawer.
- **Payouts**: individual attributed receipts — date and time, token, exact amount, USD at the saved current price, sender abbreviated with its full address on hover, trust chips — fifty at a time, filtered by UTC day, token, trust source and priced or unpriced. They open newest first. The **Date** and **USD** headers sort, each with an arrow for its direction: a click on the active header flips it, and the other header starts newest or highest first. The whole filtered set is sorted before the first fifty are cut. A USD sort uses exact decimal order, keeps unpriced receipts last in both directions, and breaks ties newest first; a date sort puts an unknown time last and keeps the report's order for equal times. The sort sits in the hash beside the filters as `sort=usd-desc`, `usd-asc` or `date-asc` (newest first is left out), survives filter changes, Clear filters and reloads, and resets when another tab opens Payouts; a ticker in the overview's token ranking opens Payouts on its token, highest USD first. The caption follows it: NEWEST FIRST, OLDEST FIRST, HIGHEST USD FIRST · UNPRICED LAST or LOWEST USD FIRST · UNPRICED LAST. On a phone the two headers show as chips above the rows. ### Rules the layout keeps

- No element adds verified and attributed together, and no chart stacks them: each group has its own figures, chart, scale and table. The attributed chart stacks only attributed tokens within a day.
- Period figures add the report's own attributed UTC day buckets, never per-receipt values and never in floating point.
- An unevaluated attributed tier reads **Not evaluated**, or **Rechecking** while rows await an attribution recheck, never 0; a local reclassification or a scan completes a pending recheck.
- Group labels, group explanations and trust-source wording are the report's fixed strings; they also appear inside popovers, the drawer and the modal. The dashboard adds no synonym for them. Its own wording is limited to figure names, the plain one-line explanation of each reason code (`REASON_TEXT` in `web/model.ts`, one per accepted code) and the name of the excluded status, which has no report group.
- Every address in an evidence view — the evidence modal, the drawer's mint, the Trust identities, the coverage samples — prints in full with a copy button, because look-alike senders share leading and trailing characters. Lists of receipts abbreviate the sender, keep the full address on hover, and open the full evidence in one step.
- Unknown and excluded records never enter a reward figure, chart, token table or the receipts list.
- USD reads to the cent everywhere, as "<$0.01" under one cent, except the evidence modal and the exact chart data tables, which keep the report's full precision.
- Copy buttons use the asynchronous clipboard API, show a visible Copied state for about two seconds, announce it through a status line, and say Copy failed rather than pretending.

An attributed row carries its **lane**, `token` or `native_sol`; the field is absent on rows recorded before the native lane, and the projection reads those as `token`. A native-SOL row's mint is the fixed sentinel rather than an address, its symbol is `SOL`, and its `sourceAta` is the distributor's own system account; the drawer and modal show no copy button or Solscan link for the sentinel. It is one more attributed asset, never summed with verified.

Unknown body fields, query strings and path encoding/traversal are rejected; the dashboard's hash route never reaches the server. JSON bodies are limited to 2 KiB, including streamed bodies; compressed bodies are rejected. Errors are short allowlisted codes, never provider/OS exceptions. Unknown failures become `dashboard_failed`.

## Job and report semantics

Admission uses the existing engine synchronously before its first asynchronous provider stage. Duplicate clicks/tabs return the active wallet job; a paused job is displayed for explicit Resume. Running tasks live in the server and are not tied to HTTP disconnects, dialog dismissal or browser lifetime. Explicit Cancel aborts the existing signal and leaves a paused checkpoint. Other scanner processes remain fenced by SQLite leases; a server restart does not steal their lease. A running record without a local task is labeled interrupted/external. Resume can be attempted after the old lease expires.

Exhausted jobs cannot be resumed under the existing engine contract. The UI explains that a new explicit check can plan missing/new ranges; it never resets counters, budgets or deadlines under Resume. If a paused/orphaned job has since expired, a new check acquires its existing fenced lease and lets engine admission retire it before starting new work. A live lease owned by another scanner remains untouched. Cancel requires the actual currently active job ID. Defaults are 200 Helius requests/pages, 10 executions, a one-hour absolute deadline, and a StonkFun budget sized when pricing starts to the discovery requests plus one per mint needing a price, at most 200. Token buckets, cooldowns, retries, page acknowledgement and fixed cutoffs remain in the engine/provider/store adapters ([SCANNER.md](SCANNER.md)). Progress shows actual stage/counters and completed ranges; total pages are unknown and no percentage is invented.

The scanner emits typed phase starts, genuine activity and phase completions from its work path. Job status includes server start/current/last-activity/finish timestamps, current phase and action, completed phases, a short event path, and phase counts only where a real denominator exists. The browser advances the visible elapsed clock from the server timestamp between status polls; polling itself never advances a phase or refreshes the last backend-activity time. Quiet provider waits remain visibly active and explicitly say the scanner is waiting; every wait the provider adapters make — pacing, a provider rate limit, retry backoff — becomes the current action, as "Waiting for provider: Helius rate limited by the provider, 2.0 s". Unknown page totals stay indeterminate; request budgets are labeled as usage. Dismiss, X and Escape hide the dialog while the header's status control keeps the job's state visible. Only Cancel aborts the worker. Refresh and reopening read server job state; completion stops the clock, and each stop of a job, complete or not, refreshes the report once. Paused, cancelled, exhausted and failed attempts retain acknowledged work and explain available continuation.

Scanning is layered ([SCANNER.md](SCANNER.md)). The progress dialog names the wallet: "Scanning <short address>: last 7 days" for a first scan and "Refreshing <short address>" for a refresh, running or stopped; its state is in the indicator, the state line and the notices beneath. A new wallet's first scan plans the last seven days, and its progress dialog says "The first scan covers the last 7 days. Older history loads afterwards in 7-day batches." under the meta line. The dialog's top line, under its title, names the span the job reads that no earlier scan saved: "Reading <start> → <end> UTC", as whole UTC days, or both times to the minute under a day, and the minute a refresh rereads before saved coverage is left out. Beneath the state line, "Now reading <day> · n of m days done" names the earliest day not saved yet, which history reads in order, and once no day remains "m of m days done". Every day count in the dialog is the job's `savedDays`, its ranges saved complete: the service serves a phase meter in days ("n / m days") from those same ranges, whatever the engine's last event said, so the two counts agree for every job kind, a rescan included; a rescan day Helius still listed differently is not counted done. A finished job's top line reads "Done: <start> → <end> · N new payouts", counted once the report after it is in view: attributed receipts inside that span, whole UTC days from the day buckets and part days from the listed receipts, never with verified ones. Every job's dialog also reads "Requests so far: Helius N · StonkFun M" from the job's `requests`. A refresh fills only the loaded range, from the oldest loaded day to its cutoff; Load earlier, a job the API starts with `kind: "earlier"`, adds seven days before it at a time down to the 2026-08-01 floor. Its dialog is titled "Loading <batch start> → <batch end> (7 days)" from the job's `batch`, and says "Usually a few minutes." until a Load earlier batch has completed, then the report's last batch, such as "Last batch: 7 days in 2 min 10 s". Coverage lists the days from the floor to the oldest loaded day as a dashed **Not loaded yet** row with its day count and the same button, apart from the failed gaps, which stay yellow. The page reads the report again each time a job stops, complete or not, so saved days of an interrupted batch show at once. Later scans use existing arbitrary-gap planning and the 60-second reconciliation overlap. Report totals use exact raw integer/decimal arithmetic; seven-day daily average divides by exactly 7. Tables preserve raw strings/decimals internally and display exact quantities. Null USD remains unavailable/unpriced. Unknown records never contribute to reward totals. A separate bounded sample shows up to 20 unknowns from the report's first 500 detail records, with aggregate counts computed over all classifications. Reason occurrences can overlap.

A stopped job's `failureClass` becomes one message in the dialog, above the phases, with "Completed days are saved: n of m." and **Retry**, which resumes the job when it can and otherwise starts the same kind again, keeping every saved day; the separate Resume button is hidden then. `key_rejected` reads "Helius rejected your API key. Check the key and try again." and adds **Re-enter API key**, which closes the dialog and opens the key form headed "Helius rejected your API key." `helius_quota` reads "Helius refused the request: <Helius's message>. A free plan may have used its monthly credits. Check usage in your Helius dashboard." `stonkfun_unreachable` reads "StonkFun's API did not respond. Try again in a few minutes.", `network` "No connection. Check your internet and try again." and `other` the raw message. `helius_rate_limited` is not a failure: while a running job waits out a Helius rate limit (`progress.waiting`), the dialog shows "Helius is limiting requests, slowing down." and keeps going; a job that stopped during one says to wait a minute and try again.

Charts display structured report UTC calendar buckets, positioned by actual calendar day. A period is a run of whole UTC calendar days. Only the first tracked day, which starts at tracking start, and the cutoff's day, which ends at the fixed cutoff, can be partial. Period figures are sums of the report's attributed day buckets inside the period, each bucket as the report rounds it to six places, added exactly. So a period can differ in its last places from a figure the report aggregates exactly, such as ALL against the since-tracking-start total. The period's daily average divides that sum by the period's calendar days, active or not, and rounds half up to six places. Payouts and tokens count the buckets' receipts and distinct tokens. Unpriced receipts are counted apart and never valued. The report's exact rolling-168-hour figure, its daily average divided by exactly 7, and the since-tracking-start figure stay available behind the info button for reference. Missing days are not synthesized as verified zero. The day tooltip's total and tokens are the report's own day bucket; a receipt's USD in Payouts is its exact amount at the mint's saved current price, rounded like every report figure, and the page never adds those per-receipt values up. The optional cumulative line on the verified chart sums priced values within the displayed buckets and uses the right scale. Prices are saved current-value observations and may be stale. Each mint is valued at its most recent saved observation that carries a USD value, from any job. A capped pass that saved only misses never unprices it. The report flags a price taken more than 24 hours before the fixed cutoff as stale, and the page shows "stale · <age>": whole hours under two days, then days to one place. A mint that never had a valued observation stays unpriced. The verified chart's no-priced-receipts state reads “No confirmed priced rewards yet.”

### Reason codes the projection accepts

`src/web/view.ts` projects only known reason strings, exported as `KNOWN_REASONS`, so an unrecognized code is dropped rather than shown; `REASON_TEXT` holds one plain line for each. Beyond the confirmation, exclusion, recheck and attributed-gate codes, the list carries: `no_token_credit_to_wallet` and `zero_value_token_credit`, the two exclusions for a transaction with no supported transfer; `credit_without_supported_transfer_instruction`, which keeps a wallet-owned credit with no supported transfer instruction — chiefly `mintTo` issuance — explicitly unknown; `native_credit_from_distributor_unproven`, which a lamport receipt from a trusted distributor carries when it fails a native-lane gate and which guarantees the row is never excluded; and `distributor_native_source_unsupported`, the native lane's own G3n failure. `no_supported_credit` stays in the list because a database saved before classifier v4 can still hold it.

## Local security model

The server binds only to `127.0.0.1` and checks the Host header against its exact IP/port, including reads, to resist DNS rebinding. It rejects foreign Origins and cross-site Fetch Metadata. Mutation Origin is mandatory; no wildcard or credentialed CORS is enabled. A static filename allowlist is read once at startup; URLs never become arbitrary filesystem paths. Security headers include restrictive CSP, no framing, no referrers, nosniff, no-store, same-origin resource policy and disabled camera/microphone/geolocation. Browser fetches are same-origin; Solscan links, and the StonkFun public reward-record links of source launches, open only upon user navigation, with no referrer. Copying uses the browser's clipboard API on this loopback origin and reads nothing from the clipboard. There is no image or network proxy.

This protects a local single-user workflow; it is not authentication against other processes running as the same OS user. Do not expose it through a tunnel or public reverse proxy. Hosted access control remains a separate future adapter responsibility.

While another dashboard holds the live database open, a finished scan's last writes can remain in `scanner.sqlite-wal`. To copy it:

1. Copy `scanner.sqlite` and `scanner.sqlite-wal` together, with shared read access.
2. Merge the log into the copy with `PRAGMA wal_checkpoint(TRUNCATE)` on the copy.
3. Serve the merged copy.

A copy of the main file alone can show that scan still running.
